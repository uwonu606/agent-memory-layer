# 기억의 상태

기억이 거치는 상태와 그 사이의 전이를 적는다. 대신하는 제품이 갖추고 출발하는 가설이고, 제품을 돌려 이 상태와 전이로 받지 못하는 경우가 나오면 다시 연다. 얹는 제품에는 후보와 올리기가 없고, 기억 파일의 판과 실림만 기록에 남는다([설계의 입구](../design.md)의 두 모양).

이 글은 뼈대만 담는다. 전이마다의 규칙과 까닭은 [저장](storing.md)과 [활용](using.md)에 있다. 이름은 코드와 기억 파일의 머리 칸에 영어로 쓰고, 낱말의 뜻은 [용어집](../../GLOSSARY.md)에 있다.

## 두 층

| 판단 | 근거 | 다시 열 조건 |
|---|---|---|
| 모두 남기는 기록(`journal`)과 세션에 싣는 기억을 가른다. 대화에서 나온 말과 기억이 바뀐 일은 모두 journal에 덧붙이고, 그 가운데 다음 세션에 실을 것만 기억이 된다 | agent가 한 일도 나중에 참조할 수 있어야 하지만, 모두 기억으로 두면 너무 많아져 관리하기 어렵다. 둘을 가르면 "한 번 말한 것도 바로 기억"과 "되풀이된 것만 기억" 가운데 하나를 고르지 않고, 말의 종류에 따라 기억이 되는 문턱을 달리할 수 있다 | 쌓이는 크기나 개인정보 때문에 말의 원문을 남길 수 없을 때 |
| 기억의 생애와 세션의 실림을 떼어 낸다. 실림은 기억의 상태가 아니라 (기억, 세션) 짝의 상태다 | 기억 하나가 여러 세션에 함께 실리고, 실린 채로 고쳐지거나 끝난다. 실림을 기억의 상태로 두면 이 둘을 받지 못한다. 운영체제로 치면 기억은 디스크의 프로그램이고, 실린 것은 그 프로그램을 띄운 process다 | 세션마다 실린 목록을 따로 들고 있을 수 없는 harness를 만날 때 |

## 흐름

```
          capture              promote           supersede, retire
journal ----------> candidate ----------> active -------------------> retired
                        |                   ^                            |
                        |                   +---------- restore ---------+
                        +------------------ retire --------------------->+

session:  active --load--> loaded --unload--> (unloaded)
```

`candidate`와 `active`는 기억 쪽에 있고, `retired`는 기록에만 있다. `supersede`는 새 판을 `active`로 만들고 옛 판을 `retired`로 보낸다.

가상의 예시 하나로 따라가면 아래와 같다.

| 일어난 일 | 전이 | 그 뒤 |
|---|---|---|
| agent가 저장소 A에서 일하다가 "이 저장소는 uv를 쓴다"고 말한다 | 없다 | 말이 journal에 남는다. 기억은 아직 없다 |
| 쌓인 말을 처리하는 쪽이 그 말을 뽑는다 | `capture` | "uv를 쓴다"가 `candidate`다 |
| 다른 세션에서 같은 말이 또 나온다 | `promote` | `active`가 된다 |
| 저장소 A에서 세션이 열린다 | `load` | 그 세션에 `loaded`다 |
| 사람이 "poetry로 바꿨어"라고 말한다 | `supersede`, `unload` | 새 판 "poetry를 쓴다"가 기억이 된다. 옛 판 "uv를 쓴다"는 `retired`가 되어 기록으로 가고, 열려 있던 세션에서 내려진다 |
| 잘못 고친 것이어서 되돌린다 | `restore` | 기록에서 옛 판 "uv를 쓴다"를 꺼내 다시 기억으로 삼는다. "poetry를 쓴다"는 기록으로 간다 |

## 상태

판은 기억 하나의 한때 모습이다. 책의 개정판과 같아서, 기억을 고치면 새 판이 기억이 되고 옛 판은 기록으로 간다.

| 상태 | 뜻 | 실리나 |
|---|---|---|
| `candidate`(후보) | 한 번 나온 말이다. 아직 기억이 아니다 | 싣지 않는다 |
| `active`(기억) | 기억이 되어 실릴 수 있다. 기억의 지금 판이다 | 걸리는 세션에 싣는다 |
| `retired`(끝남) | 더는 쓰지 않는 판이다. 기억 쪽에서 빠지고 기록에 남는다. 끝난 까닭을 지닌다 | 싣지 않는다 |
| `loaded`(실림) | 기억의 상태가 아니라 (기억, 세션) 짝의 상태다 | 실린 것이다 |

끝난 까닭은 다섯이다.

| 까닭 | 뜻 |
|---|---|
| `rejected` | 사람이 기억하지 말라고 했다. 이것만은 기억 쪽에 싣지 않는 표시로 남아, 같은 주제가 그 scope에서 다시 뽑히지 않게 막는다 |
| `superseded` | 새 판으로 바뀌었다 |
| `stale` | 낡았다 |
| `wrong` | 사람이 틀렸다고 표시했다 |
| `expired` | 후보인 채로 기한이 지났다 |

| 판단 | 근거 | 다시 열 조건 |
|---|---|---|
| 새 말은 막지 않고 후보로 받고, 기억으로 올리는 일은 따로 한다 | 받는 일과 올리는 일을 가르면 그 작업에서만 쓰는 말이 기억이 되지 않는다. 이름 목록을 오래 관리해 온 쪽이 같은 모양을 쓴다. 통제 어휘 표준 ANSI/NISO Z39.19는 목록에 없는 말을 candidate term으로 받아 표시를 달고, 승인되면 정식 term으로 올린다 | 후보가 기억으로 올라가기 전이라 필요한 기억이 닿지 않는 일이 시험에서 되풀이될 때 |
| 기억 쪽에는 지금 판만 둔다. 옛 판과 끝난 기억은 까닭과 함께 기록으로 가고, 기록에서는 지우지 않는다 | agent가 묻지 않고 기억을 고치므로, 잘못 고치거나 잘못 끝낸 것을 되돌릴 길이 있어야 한다. 되돌릴 때 필요한 것은 옛 판 하나이고, 기록은 원래 모든 말과 바뀐 일을 남기는 층이어서 따로 보관할 것이 생기지 않는다. 옛 판을 기억 쪽에 두면 낡은 값이 지금 값과 같은 자리에 쌓여 지금 사실처럼 읽힐 수 있다. 지우지 않고 대체를 적는 사례가 여럿이다. Wikidata는 합친 옛 항목을 redirect로 남기고 다시 쓰지 않는다. Graphiti는 끝난 관계를 지우지 않고 `invalid_at`으로 무효를 적는다 | 지난 판을 지금 판 곁에서 바로 보아야 하는 일이 잦을 때 |

## 전이

| 전이 | 어디서 → 어디로 | 계기 | 자세히 |
|---|---|---|---|
| `capture`(뽑기) | journal의 말 → `candidate` | 쌓인 말을 처리하는 쪽이 기억에 둘 만한 말을 뽑았을 때 | 저장 |
| `promote`(올리기) | `candidate` → `active` | 서로 다른 세션에서 되풀이될 때, 사람의 결정이 분명할 때, 사람이 "기억해"라고 할 때 | 저장 |
| `supersede`(고치기) | 옛 판 `active` → `retired`, 새 판 → `active` | 문장이나 scope가 바뀔 때 | 저장 |
| `retire`(끝내기) | `candidate`·`active` → `retired` | 사람이 "기억하지 마"라고 할 때, 낡았을 때, 사람이 틀렸다고 표시할 때, 후보의 기한이 지났을 때 | 저장 |
| `restore`(되돌리기) | `retired` → `active` | 기록의 판을 되살릴 때. 그 자리에 있던 같은 주제의 기억은 `retired`가 된다 | 저장 |
| 다시 묶기 | scope를 줄이거나 넓힌 새 판 | 같은 주제의 다른 문장이 겹치는 scope에 나올 때(나누기), 같은 문장이 다른 저장소에서 나올 때(합치기) | 저장 |
| `load`(싣기) | (기억, 세션) → `loaded` | 세션의 싣는 자리에 왔을 때 | 활용 |
| `unload`(내리기) | `loaded` → 내림 | 대화가 요약으로 바뀔 때(compaction), 그 기억이 끝났을 때, 같은 주제의 더 가까운 기억이 생겼을 때 | 활용 |

세션의 끝은 계기로 쓰지 않는다. 세션은 끝을 알리지 않고 닫히거나 나중에 이어질 수 있어서, 끝을 알 수 없다.

## 칸

기억은 사람이 읽는 markdown 파일이고, 상태와 아래 칸은 파일의 머리에 적는다. 기록으로 간 판도 같은 칸을 지닌 채로 남는다.

| 칸 | 뜻 | 쓰이는 전이 |
|---|---|---|
| `origin`(출처) | 어디서 생겼나. journal의 자리다. 생길 때 한 번 쓰고 바꾸지 않는다 | `capture` |
| `applies_to`(scope) | 어디서 쓰이나. 대상(저장소, 일의 갈래, 사람, 기기)의 목록이다 | `load`, `supersede`, 다시 묶기 |
| `subject`(주제) | 무엇에 관한 것인가. 같은 것인지 알아보는 열쇠다 | `capture`, `restore` |
| `decided_by`(정한 쪽) | 사람이 분명히 시켜서 정한 것인가. 그러면 `human`이고, 도구가 스스로 한 것이면 `agent`다 | `promote`, `restore`, 고치기와 끝내기의 조건 |
| `kind`(종류) | 어떤 종류의 기억인가, 지금 상태를 적은 것인가 | `capture`, `supersede` |
| `evidence`(근거) | 저장소에 대 보는 검사 목록이다. 대 볼 것이 없는 기억은 비어 있다 | `capture`, `supersede`, `load`의 조건 |
| `expires`(기한) | 지금 상태를 적은 기억에만 있다 | `capture`, `load`의 조건 |

근거, 기한, 그 말이 나온 세션은 기억 하나에 한 값으로 두지 않고 scope의 대상마다 둔다. 까닭은 [저장](storing.md)의 다시 묶기에 있다.

| 판단 | 근거 | 다시 열 조건 |
|---|---|---|
| 상태 값은 닫힌 목록이다 | 기계는 값이 목록 안에 있는지와 칸 사이의 모순만 검사하고, 상태를 바꾸는 판단은 전이가 한다. Python의 PEP와 Kubernetes의 KEP가 문서의 상태를 닫힌 목록으로 둔다 | 어느 상태에도 맞지 않는 기억이 나올 때 |

## 기록

모든 전이는 journal에 한 줄을 남긴다. 줄에는 누가, 언제, 어느 전이를 했는지가 들어간다. 판이 생길 때마다 그 판을 기록에 적는다. 그래서 기억이 고쳐지거나 끝나도, 사람이 기억 파일을 직접 고쳐도 옛 판은 이미 기록에 있다.

그래서 아래 넷은 따로 장치를 두지 않고, journal의 줄을 다르게 읽는 것이 된다.

| 읽는 것 | journal에서 읽는 줄 | 자세히 |
|---|---|---|
| 내력 | `origin`이 가리키는 말과 전이 줄 | [저장](storing.md) |
| 쓰임 | 기억마다의 `load` 줄과 검사 결과 | [활용](using.md) |
| 실패 | 전이가 실패한 줄, 싣다가 덜어 낸 줄 | [저장](storing.md), [활용](using.md) |
| 비용 | 실은 글자 수, 모델 호출 수, 걸린 시간 | [비용](cost.md) |

## 검증

[tools/state-check](../../tools/state-check/README.md)가 이 글의 뼈대와 저장·활용 글의 규칙을 모델 없는 상태 기계로 옮겨 돌린다. 아래는 2026-11-25에 돌린 결과다.

| 돌린 것 | 결과 |
|---|---|
| 기계가 받아야 하는 경우 69개 | 모두 받는다 |
| 무작위 조작 2000회 × 40걸음을 씨앗 여덟으로, 불변식 열둘 | 위반 0 |
| 기계를 한 곳씩 망가뜨린 변이 44개 | 경우나 불변식이 모두 잡는다 |
| 무작위 조작으로 닿은 상태 | 넷 모두 |

확인한 것은 모델 없는 상태 기계가 이 경우들에서 기대대로 움직인다는 데까지다. 실제 harness에서 돌린 것이 아니다.

상태 기계가 아니라 다른 부품이 맡는 경우는 열다섯이고, 도구의 `OUT` 목록에 주인과 함께 있다. 주인은 뽑을 말을 거르는 일, 싣는 자리, 실린 동안의 검사, 같은 말을 알아보는 일, 화면, 기록을 읽는 일, 저장 배치, 테스트셋이다. 불변식의 목록과 도구가 넣지 않은 것은 도구의 README에 있다.
