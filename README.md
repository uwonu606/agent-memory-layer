# agent-memory-layer

코딩 agent의 기억을 사람이 읽는 파일로 두고, 일마다 필요한 기억만 agent에게 주어 그대로 따르게 하며, 기억이 생기고 쓰이고 고쳐지는 과정을 사람이 읽어서 알고 되돌릴 수 있게 하려는 도구다. 지금은 설계와 테스트셋을 쓴 단계이고, 이 도구의 구현은 아직 없다.

코딩 agent의 기억 기능을 쓰다가 불편을 겪은 개발자가 읽는 글이다. 이 도구가 어떤 문제를 풀려는지, 지금 있는 도구는 그 문제를 어떻게 푸는지, 어떤 순서로 만들고 어디까지 왔는지를 적는다.

## 문제

기억 도구를 쓰는 사람이 겪는 문제를 열한 갈래로 나눴다. 만든 사람이 겪은 것과, 여러 기억 도구의 issue와 쓰는 사람의 글에 적힌 것을 모았다.

| 갈래 | 쓰는 사람이 겪는 것 |
|---|---|
| 보임 | 답이 기억 때문인지 모델이 스스로 꺼낸 것인지 가를 수 없다. 기억이 일을 망치는 줄 몰랐다가, 지우고서야 안다 |
| 닿음 | 기억이 길어지자 오래된 설정값이 실리지 않아 한 시간을 잃었다. 기억에 적힌 것과 다른 말로 부르면 불려 오지 않는다. 하루 일했는데 기억이 하나도 없다 |
| 따름 | 기억을 찾아 놓고 무시한다. 사람이 따로 검토를 시킬 때만 따른다. 긴 세션에서 흐려진다 |
| 끼어듦 | 다른 프로젝트의 사실, 한 프로젝트에서만 한 말, 이미 낡은 상태가 답의 근거로 나온다. 개인 프로젝트 작업 중에 직장 일이 섞였다. 일마다 "메모리 쓰지 마"를 붙였다 |
| measurement | 벤치마크 점수는 괜찮은데 날마다 받는 결과는 묽었다. 기억을 감사해 보니 약 310개 가운데 65%만 맞았다는 보고(`github/copilot-cli#2278`)와 10,134개 가운데 97.8%가 쓸모없었다는 보고(`mem0ai/mem0#4573`)가 있다 |
| 내력 | 기억이 언제 왜 생겼는지, 어떻게 바뀌었는지 모른다 |
| 한 곳 | 기억 파일이 저장소마다 따로 있고 폴더 이름을 읽기 어렵다 |
| 고침 | 낡은 기억을 말 한 번으로 고치지 못한다. 사람은 다른 이름으로 부르는데 기억에는 다른 낱말로 적혀 있다 |
| 기억이 맞다 | 하지 않은 말, 예시 문장, 다른 세션의 일이 사실로 적혀 있다. 뒤에서 도는 기억 정리가 지나가듯 한 말 때문에 맞는 기억을 지웠다. 밤사이 고쳐진 것을 미리 볼 수 없었다. 가정으로 한 질문이 사실처럼 쓰였다 |
| 조용한 실패 | "저장됐다"는 표시를 봤는데 나중에 찾으면 없다. 기억이 많아지면 뒤쪽에 적힌 규칙이 알림 없이 잘린다 |
| 숨은 비용 | 기억 도구를 켜면 사용 한도가 빨리 차고, 찬 뒤로는 기억도 멈춘다. 시작부터 사용량이 크다. 몇 달 뒤에는 기억을 넣거나 물을 때마다 1분 넘게 기다린다 |

## 지금 있는 도구

기억 도구 스물넷의 문서와 issue를 2026년 11월에 읽고, 갈래마다 가장 멀리 간 방식과 거기에 못 미치는 모습을 적었다. Claude Code만 실제 세션으로 봤고 나머지는 읽기만 했다. 도구는 바뀌므로 그때의 모습이다.

| 갈래 | 가장 멀리 간 방식 | 못 미치는 곳 |
|---|---|---|
| 보임 | 기억을 실을 때 개수와 token 추정치를 보이고, 모델에게 출처를 밝히라고 지시한다(Supermemory plugin). 답 아래에 Sources를 붙이거나(ChatGPT) 모델이 답 끝에 citation을 붙인다(Codex) | Claude Code는 실린 기억을 화면에 보이지 않고, 읽은 기억은 개수 한 줄로만 보인다 |
| 닿음 | 도구 호출마다 기억 전체를 훑거나(claude-map-reduce-memory) 사람의 말마다 검색한다(Supermemory plugin) | 최근 것부터 골라 관련 있는 것이 빠지고(claude-mem, MemPalace), agent가 기억 도구를 부르지 않는다(engram, MemPalace, Serena). 말마다 검색하는 Supermemory plugin은 검색 문턱이 낮아 관계없는 기억이 거의 매번 실린다는 보고를 받았다 |
| 따름 | 지시문에 기댄다. 스물넷 가운데 실린 기억대로 하게 만드는 다른 장치를 둔 도구는 찾지 못했다 | 지시문만으로는 긴 세션과 많은 지시에서 흔들린다 |
| 끼어듦 | 기억의 근거가 된 코드 위치를 지금 코드에 대 보고 기한을 둔다(Copilot). 사실마다 유효 기간을 둔다(Zep). 프로젝트 안에서만 쓰는 기억을 둔다(ChatGPT). 대화 하나만 기억을 끈다(ChatGPT, Codex, Copilot CLI) | 프로젝트를 폴더 이름으로 알아보는 도구는 한 프로젝트의 기억이 둘로 쪼개지거나(claude-mem, MemPalace) 다른 프로젝트와 섞인다(agentmemory, engram). 같은 프로젝트에 함께 연 세션끼리 기억이 섞인다는 보고도 있다(claude-mem, ai-memory) |
| measurement | 실제 작업을 기억 켬과 끔으로 갈라 잰다(Copilot). 사람이 기억에 helpful, stale, wrong을 표시하거나(ai-memory) 답의 출처가 관련 있는지를 표시한다(ChatGPT) | 실제 작업으로 잰 곳은 Copilot 하나다. 나머지는 재지 않거나, 수치가 있어도 대화를 묻고 답하는 벤치마크의 점수다 |
| 내력 | 기억이 바뀔 때마다 git commit과 까닭을 남긴다(Letta MemFS). 까닭을 필수 칸으로 둔다(ByteRover). 기록마다 시각, 세션, 원본 도구 입출력을 남긴다(claude-mem) | Claude Code는 마지막으로 고친 시각과 처음 쓴 세션만 남기고, 까닭은 남기지 않는다 |
| 한 곳 | DB나 서버 하나에 모은다(claude-mem, MemPalace, agentmemory, engram, ai-memory) | Claude Code는 저장소마다 폴더를 따로 둔다 |
| 고침 | 말 한 번으로 고친다(Letta MemFS의 `/remember`). 주제 key가 같으면 새 값으로 바꾼다(engram). 새 판을 만들고 옛 판을 보관한다(agentmemory) | 지우기만 되거나(claude-mem) 전체를 비우기만 되는 도구가 있다(claude-map-reduce-memory) |
| 기억이 맞다 | 저장할 때 승인을 물을 수 있다(Copilot). 지울 때만 묻는다(Serena). 쓰기 전에 승인을 기다리는 대기열을 둔 적이 있다(ByteRover V3) | 하지 않은 말이나 예시 문장이 사실로 적혔다는 보고가 있다(ByteRover, Supermemory, claude-mem). 묻지 않고 쓰는 도구가 여럿이다(claude-mem, Supermemory, engram, agentmemory) |
| 조용한 실패 | 최근에 나온 열둘 가운데 실패를 알리는 도구는 Letta MemFS 하나다 | 실패해도 일을 막지 않는 것이 공통 원칙이어서, 알리지 않는 도구에서는 실패가 조용히 지나간다. Letta MemFS는 같은 알림을 되풀이한다는 보고를 받았다 |
| 숨은 비용 | 기억이 쌓여도 세션이 시작할 때 쓰는 양을 작게 묶는다고 말한다(Beads, agentmemory, claude-mem) | 도구 설명문만으로 turn마다 수천 token을 쓰는 도구가 있다(ai-memory) |

갈래를 가로질러 보면 넷이 보인다.

- 따름은 지시문 말고 다른 장치를 둔 도구를 찾지 못했고, measurement는 실제 작업으로 잰 곳이 하나뿐이다.
- 끼어듦은 같은 일을 무엇으로 알아보느냐에서 먼저 갈린다.
- 보임과 내력은 빌릴 방식이 있다. 실을 때 출처를 붙이는 것과, 바뀔 때마다 까닭을 남기는 것이다.
- 기억이 맞다에서 가장 멀리 간 방식은 사람의 승인이다. 이 도구는 사람을 기다리게 하지 않으려고 승인을 기본으로 두지 않고, 묻지 않고 쓰되 바뀐 것을 알리고 되돌릴 수 있게 한다. 까닭은 아래 전제에 있다.

## 전제

모든 갈래에 걸리는 가정이 하나 있다. 사용자는 메모리를 신경 쓰지 않고 개발한다. 그래서 기억은 사람의 표시 없이 생기고, 실리고, 고쳐져야 하고, 사람에게 기다림이나 행동을 요구하는 방식은 기본값으로 두지 않는다. 대신 agent가 바꾼 것은 사람이 알 수 있고 되돌릴 수 있게 한다.

사람의 손이 닿는 곳은 둘이다. 놓친 기억을 알아챘을 때 단서를 말해 되찾는 것, 그리고 원할 때만 쓰는 지름길이다. "기억해", "어디서나", 고쳐 달라는 말 같은 것이다. 일하는 화면에 뜨는 알림은 알리기만 하고 할 일을 요구하지 않는다.

## 원하는 것

갈래마다 쓰는 사람 쪽 말로 적은 성공의 문장이다. 가설이고, 만든 것을 돌려 본 뒤 고친다. 문장에 나오는 낱말은 아래와 같다.

| 낱말 | 뜻 |
|---|---|
| 실린다 | 기억이 세션에 들어가 agent가 읽게 된다 |
| 닿는다 | 그 일에 필요한 기억이 실린다 |
| scope | 기억이 쓰이는 곳이다. 저장소, 일의 갈래, 사람, 기기로 적는다. 지금 세션에는 저장소가 가장 가깝고 사람과 기기가 가장 멀다 |
| 일의 갈래 | 저장소 여럿을 묶는, 사람이 일하는 단위다. 직장 일, 개인 프로젝트 같은 것이다 |
| 걸린다 | 기억의 scope가 지금 세션과 겹친다 |
| 근거, 기한 | 근거는 기억이 아직 맞는지 저장소에 대 보는 검사이고, 기한은 금방 바뀌는 사실에 붙이는 마지막 날이다 |

| 갈래 | 원하는 것 |
|---|---|
| 보임 | 이번 일에 어떤 기억이 실렸는지 묻지 않고도 보인다 |
| 닿음 | 그 일에 필요한 기억은 아직 맞는 한, 오래됐든, 다른 저장소에서 남겼든, 내가 다른 말로 불러도 닿는다. 놓친 것은 내가 낱말이나 그 기억이 있던 곳 같은 단서를 말하면 찾을 수 있다 |
| 따름 | 닿은 기억은 따로 시키지 않아도 처음부터, 긴 세션의 끝까지 따른다 |
| 끼어듦 | 지금 일에 걸리지 않는 기억은 내가 막지 않아도 실리지 않는다. 다른 저장소나 다른 일의 갈래에서 남긴 것, 한 곳에만 준 말, 같은 주제의 옛 값과 더 먼 scope의 값, 근거가 어긋나거나 기한이 지난 것, 그 작업에서만 한 말이 그렇다 |
| measurement | 기억마다 언제 얼마나 실렸고 실린 뒤 그대로 했는지가, 내가 표시하지 않아도 남아 있어서 읽어서 안다 |
| 내력 | 기억마다 언제, 어디서, 어떤 말에서 생겼는지와 그 뒤 언제 무엇 때문에 바뀌었는지가, 내가 따로 적지 않아도 남아 있어서 agent에게 묻지 않고 읽어서 안다 |
| 한 곳 | 모든 기억을 한 자리에서 보고, 기억마다 어디에 걸리는지를 읽어서 안다 |
| 고침 | 낡은 것을 내가 부르는 말로 한 번 말하면, 관련된 기억이 모두 고쳐지고 나머지는 그대로이며, 잘못 고친 것은 되돌릴 수 있다 |
| 기억이 맞다 | 기억은 나와 agent가 실제로 한 말에서만 생긴다. 예시로 든 문장이나 가정으로 한 질문은 기억이 되지 않는다. 나와 agent가 한 것들은 기록되고, 둘은 구분되며 무엇이 바뀌었는지 볼 수 있고 되돌릴 수 있다. 사람이 쓰거나 고친 것도 agent가 한 것과 똑같이 기록되고 되돌릴 수 있어야 한다 |
| 조용한 실패 | 저장이 실패하거나 기억이 잘리면 나에게 보인다. 그래도 일은 멈추지 않는다 |
| 숨은 비용 | 기억 도구가 쓴 사용량과 시간, 차지한 context 자리가 나에게 보이고, 기억이 쌓여도 그것이 함께 불어나지 않는다 |

닿음과 끼어듦은 기억이 남은 곳과 쓰이는 곳을 갈라서 함께 채운다. 다른 저장소에서 남긴 기억이어도 scope가 지금 세션과 겹치면 싣고, 겹치지 않으면 싣지 않는다. 닿음의 "오래됐든"은 주제가 다른 옛 기억이 최근 것에 밀려 빠지는 경우를 가리킨다. 같은 주제의 옛 값은 실리지 않아야 한다.

기억이 일을 실제로 낫게 했는지는 쓰는 자리에서 재지 않는다. 만드는 쪽이 테스트셋에서 기억을 켠 쪽과 끈 쪽을 견주어 잰다. 그 밖의 낱말은 [용어집](GLOSSARY.md)에 있다.

## 만드는 것

도구는 두 쪽으로 이루어지고, 한쪽만으로는 원하는 것을 채우지 못한다. 기억을 어떤 단위로 어떤 이름을 붙여 저장하느냐가 무엇을 골라 실을 수 있는지를 정하므로, 두 쪽을 따로 설계하지 않는다.

| 쪽 | 무엇 | 설계 |
|---|---|---|
| 저장 | 기억이 생겨서 제자리에 놓이고 고쳐지는 길 | [저장](docs/design/storing.md) |
| 활용 | 놓인 기억이 일하는 세션에 닿아서 답을 바꾸는 길 | [활용](docs/design/using.md) |

이 도구는 코딩 agent에 원래 들어 있는 기억 기능을 끄고 그 자리를 대신한다. Claude Code에서는 원래 기능이 기억을 실을 때 바깥 도구에 알리는 자리가 없어서 무엇이 실렸는지 받아 볼 수 없고([Claude Code의 구조와 동작](docs/claude-code/structure.md)), 둘을 함께 켜 두면 답에 쓰인 기억이 어느 쪽에서 왔는지 가를 수 없기 때문이다. 이미 쌓인 기억은 지우지 않고 받는다.

두 쪽이 무엇으로 이루어지고 말 하나가 기억이 되어 쓰이기까지 어떤 차례를 거치는지는 [설계의 입구](docs/design.md)의 큰 그림에 있다.

## 첫 목표

이 도구의 구현 하나가 아래 한 사이클을 실제 agent에서 이어 도는 것이다. 도는지는 아래 네 걸음을 처음부터 끝까지 잇는 시험으로 재고, 아직 이루지 못했다.

| 걸음 | 하는 일 |
|---|---|
| 받기 | 이미 쌓인 기억을 사실 하나씩으로 나눠 받는다 |
| 싣기 | 세션이 시작할 때 그 일에 걸리는 기억이 실리고, 실린 것이 화면에 보인다 |
| 쓰기 | 새 기억이 남고, 언제 어디서 어떤 말에서 생겼는지가 기록에 적힌다 |
| 고치기 | 낡은 기억을 사람의 말로 찾아 고치고, 잘못 고친 것은 되돌린다 |

## 만드는 방식

구조나 구현보다 원하는 것을 먼저 보고, 아래 여섯 걸음으로 만든다. 다섯째 걸음에서 앞의 걸음으로 돌아가므로 한 번 지나가는 줄이 아니다. 걸음마다 그 일을 가리키는, 이미 있는 이름을 곁에 적었다.

이 글에서 제품은 같은 테스트셋으로 견주려고 만드는, 이 도구의 구현 하나를 가리킨다. 기준선은 견줄 때 기준으로 삼는, 코딩 agent에 원래 들어 있는 기억 기능이다.

| 걸음 | 이 도구에서 하는 일 | 이미 있는 이름 |
|---|---|---|
| 1. 상황 보기 | 기억 도구를 쓰는 사람이 실제로 어디서 틀어지는지를 모은다. 위의 문제 열한 갈래다 | Jobs to Be Done, Double Diamond의 Discover, error analysis |
| 2. 성공 적기 | 갈래마다 성공을 쓰는 사람 쪽 말로 적고, 구현 이야기는 넣지 않는다. 위의 원하는 것이다 | Working Backwards, Parnas의 requirements document |
| 3. 판정할 시험 만들기 | 테스트셋을 제품보다 먼저 만든다. 하나로 다 재지 않고 부품, 기능, 전체의 세 층으로 나누며, 통과와 실패로만 가른다. 시험마다 통과하는 답 하나를 먼저 보여 풀 수 있는 시험인지 확인한다. 손으로 만든 답이어도 된다 | eval-driven development, reference solution |
| 4. 기준선 재기 | 가장 단순한 해인 기준선을 테스트셋에 먼저 돌린다 | baseline, simplest solution |
| 5. 출력 보고 고치기 | 제품을 여럿 빠르게 만들어 같은 테스트셋으로 견준다. 돌린 출력을 읽고 테스트셋을 고친 뒤 모든 제품을 다시 돌린다 | criteria drift, plan to throw one away |
| 6. 구조 정하기 | 제품마다 달라지는 구조는 먼저 정하지 않는다. 언제 싣는지, 실린 기억대로 하게 만드는 법 같은 자리는 선택지마다 제품으로 만들어 견준 결과로 가린다 | Canon TDD의 refactor |

걸음 밖에서 정해 둔 것은 아래와 같다.

- 모든 제품이 같게 갖출 것은 가설로 먼저 적었다. 기억이 거치는 상태와, 저장과 활용의 규칙이다. 제품을 돌려 이 가설로 다루지 못하는 경우가 나오면 다시 연다. 아래 지금 상태의 설계와 상태 검증이 이 가설을 적고 확인한 일이다.
- 제약은 처음에 정하지 않는다. 한 사이클이 돈 뒤에 실제로 지켜진 것을 제약으로 적는다.
- 만드는 동안의 안전장치는 둘이다. 이미 쌓인 기억의 원본을 지우지 않고, 실제 home에 놓기 전에 격리된 home에서 먼저 돌린다.
- 기억의 원본을 사람이 읽는 markdown 파일로 두는 데서 출발한다.

판단마다의 근거는 [판단과 방향](docs/direction.md)에 있다. Claude Code에서 먼저 만든다. Claude Code에 붙는 자리와 기대는 동작은 [Claude Code 동작](docs/claude-code.md)에 있다.

## 지금 상태

만드는 방식의 셋째 걸음인 테스트셋을 썼고, 넷째 걸음인 기준선을 돌리기 전이다.

| 일 | 상태 |
|---|---|
| 조사 | 기억 도구와 이웃 분야가 열한 갈래를 푸는 방식을 읽었다. 판단에 쓴 것은 설계 글의 근거에 적었다 |
| 설계 | 모든 제품이 갖출 것, 제품마다 달리 만들어 견줄 자리, 조건을 붙여 미룬 것을 적었다. [설계의 입구](docs/design.md) |
| 상태 검증 | 기억이 거치는 상태와 전이를 LLM 없이 도는 상태 기계로 옮겨 돌렸다. 설계가 다뤄야 하는 경우 69개가 기대대로 움직이고, 불변식 열둘의 위반이 없다. 확인한 것은 설계가 스스로 어긋나지 않는다는 데까지이고, 실제 agent에서 돌린 것이 아니다. [tools/state-check](tools/state-check/README.md) |
| 테스트셋 | 세 층으로 썼다. 시험마다 통과하는 답 하나를 보이는 일이 남았다. 제품을 만드는 agent가 정답을 보고 맞추지 않게 테스트셋은 저장소 밖에 둔다 |
| 기준선 | Claude Code에 원래 들어 있는 기억 기능을 테스트셋에 돌려 견줄 기준으로 삼는다. 아직 돌리지 않았고, 돌리면서 비용의 예산 값을 정한다 |
| 제품 | 아직 없다. 구조를 고르기 전에 만든 거친 도구로 한 사이클을 한 번 이어 돌려 본 적이 있다. 그것은 제품이 아니고 테스트셋으로 잰 것도 아니어서 첫 목표로 세지 않는다. 거기서 막힌 것은 [거친 도구가 붙은 자리](docs/claude-code/integration.md)에 있다 |
